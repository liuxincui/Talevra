# Talevra 系统架构约束

## 核心原则

系统固定分为三层，依赖只能自上而下：

```text
页面和交互层
      ↓
通用业务模块层
      ↓
基础设施层
```

下层不能依赖上层，同层模块避免相互穿透。底层实现或第三方 SDK 发生变化时，由通用业务模块层消化，上层页面的调用方式保持不变。

## 1. 页面和交互层

**职责**：页面展示、用户操作、路由、页面状态和可复用 UI 组件。

**目录**：`lib/features/`、`lib/app/`，通用 UI 可放在 `lib/shared_ui/`。

**约束**：

- 页面只描述“用户要做什么”，不处理网络协议、SDK 参数、鉴权细节和原始数据解析。
- 页面通过通用业务模块提供的接口完成分享、登录、请求、验证、埋点等操作。
- 跨页面复用交互和组件；具体业务页面之间不直接依赖。
- 禁止直接引用 `dio`、`shared_preferences` 或广告、支付、归因、社交等第三方 SDK。

## 2. 通用业务模块层

**职责**：向页面提供稳定、统一的业务能力，并隔离基础设施和第三方实现的变化。

**建议目录**：`lib/services/`，按能力拆分模块，例如：

```text
services/
  api/          API 定义、请求编排、错误映射
  auth/         登录状态与登录流程调度
  share/        分享能力
  sdk/          第三方 SDK 接入和生命周期管理
  locale/       语言选择与切换
  parser/       通用响应和数据解析
  validation/   通用校验
  analytics/    埋点定义、收集和转发
```

**约束**：

- 对上提供项目自有接口、模型和错误类型，不暴露第三方 SDK 对象或返回值。
- 一个外部能力只有一个接入入口；页面和具体功能模块不得绕过该入口。
- SDK 初始化、配置、调用、回调转换和异常处理全部收口在本层。
- API 地址、请求方法、字段解析、错误码映射和登录失效处理全部收口在本层。
- 本层可以依赖基础设施层，但不能依赖任何具体页面或 Widget。

## 3. 基础设施层

**职责**：提供与具体业务无关的底层能力。

**目录**：`lib/core/`，包括：

- 网络客户端、拦截器和连接配置；
- 本地存储、缓存和设备能力封装；
- 日志、时间、金额、签名、幂等键等通用工具；
- 环境、品牌和构建配置。

**约束**：

- 不包含页面语义或具体业务流程。
- 不依赖 `features/`、`app/` 或 `services/`。
- 对外提供小而稳定的基础能力，不承载某个页面专用逻辑。

## 依赖红线

以下写法一律视为架构偏离：

- 页面直接调用网络客户端、存储实例或第三方 SDK；
- 页面直接解析原始 JSON、处理服务端错误码或拼装签名参数；
- 基础设施层引用业务模型、页面状态或 Widget；
- 为赶进度在页面中新增一次性的 SDK/API 调用，后续再封装；
- 两个具体功能模块直接复用彼此的内部实现。

## 新功能落位检查

新增功能前依次判断：

1. 只与展示和操作有关：放页面和交互层。
2. 是多个页面可复用的业务能力，或需要隔离 API/SDK 变化：放通用业务模块层。
3. 与业务无关，属于网络、存储、日志或纯工具：放基础设施层。
4. 页面是否只依赖稳定接口，而没有直接接触底层或第三方类型。
5. 替换网络库或 SDK 时，是否无需修改页面代码。

## 当前工程说明

现有 `lib/features/` 和 `lib/core/` 分别对应上层与底层。后续新增或整理分享、SDK 管理、语言切换、API 管理、解析、登录调度、验证和埋点能力时，统一收口到 `lib/services/`；已有代码按功能迭代逐步迁移，不为目录调整单独做大规模重构。
